## Threat model and recovery contract

Threats include simultaneous REST/MCP requests, independent buyer/seller processes, process termination at persistence boundaries, lost TCP/RPC acknowledgements, incomplete or altered journals, storage errors, stale account/history responses, deadline races, hostile source URLs, changing artifacts, malicious container processes, and hostile browser/operator fields. The server filesystem and configured signer/profile registries remain trusted. Journal checksums detect corruption and accidental substitution; they are not authentication against a hostile OS administrator.

Application classifications are `PROVEN_NOT_OCCURRED`, `PROVEN_OCCURRED`, `SAFE_TO_RETRY`, `UNKNOWN_EXTERNAL_EFFECT`, `UNKNOWN_FINANCIAL_OUTCOME`, and `RECONCILIATION_REQUIRED`. They are not Anchor states. An unresolved intent is retained. Missing acknowledgement is not evidence of non-execution. Unknown outcomes never cause automatic replacement execution or financial submission. `SAFE_TO_RETRY` is evidence returned by read-only inspection, not an implemented restart resubmission worker.

## Implemented hardening and failures discovered

1. **Immutable quotes and durable claims.** Independent controllers could overwrite their first quote. Exclusive publication now selects one canonical quote and binds buyer/task/service/input/privacy across REST and MCP. Persistent funding/execution claims supplement in-memory serialization.
2. **Journal corruption and publication failures.** Null/incomplete or syntactically valid altered result/manifest files could be mistaken for useful saved state. New journals use strict key-bound checksummed envelopes, exclusive publication or atomic replacement, file flush, validated read-back, and fail-closed reads. Valid legacy manifests/results remain readable only after validation. Stale temporary files are not activated.
3. **Funding/settlement retry evidence.** Processed signatures were accepted and stale-blockhash error strings alone could trigger transaction reconstruction. Signed signature, blockhash, last-valid block height, instruction fingerprint, and timestamp now persist before submission. Rebuild requires rooted expiry/finalized failure, slot-fenced signature history and fresh account eligibility. A newer height read paired with an older slot was reproduced and fixed by obtaining block height from the exact finalized block.
4. **Orphan and mismatched evidence.** Prepared/completed records without an intent, changed financial instruction bindings, and intent-without-signature windows block automatic retry. Existing intent without prepared bytes can belong to a concurrent writer and is unknown, not proof of non-occurrence.
5. **Stale cached outcomes.** A saved funded/settled response could override absent or Pending chain state. Fresh state now determines chain action and conflicts request reconciliation. Cached funding additionally invokes read-only confirmation/memo validation; account disappearance cannot turn this validation into initialization.
6. **Recovered receipts.** Coordinator catches could promote an ambiguous signature using final TaskState alone; funding could suppress memo failure. Recovered public/private settlement, refund, cancellation and funding now require successful confirmed/finalized signature evidence plus matching account outcome. Funding also verifies a successful transaction containing the expected memo. Missing, processed, failed or unavailable signature evidence does not create a confirmed receipt.
7. **Seller execution persistence.** Seller execution intents flush before dispatch; saved results are checked, flushed, atomically published and validated. Independent instances cannot claim the same task twice. A process that dies after a simulated effect receipt but before result storage leaves an unresolved durable intent, not permission to execute again.
8. **Result/report restart.** Production runtime stores immutable validated raw result envelopes before verification and linked reports before settlement. Restart can reverify a saved result without seller POST; lost-response recovery uses read-only seller GET. A report alone does not authorize settlement. The same persisted source challenge is reused.
9. **Private issuance.** Previously a restarted voucher client generated fresh random blind material. Runtime now persists one issuance intent and exact material before requesting a signature, then stores and verifies the response. Completed replay reconstructs the same voucher; a lost response blocks automatic replacement.
10. **Verifier termination.** `finally` cannot clean up after a killed verifier. Owned-container leases now persist before container creation; an in-container trusted timeout bounds execution independently of the parent. Restart removes only validated containers with proven dead owners and fixed temporary input files. Daemon failure retains the lease and fails closed.
11. **Clock authority.** Seller expiration and coordinator cancellation now use Solana Clock, preserving exact deadline semantics independently of browser/host time. Safety margin remains separate from source freshness skew and all network/sandbox timeouts.

Red-before-fix evidence included the initial six failing retry/journal/quote tests, three malformed-manifest failures, stale funded/settled regressions, exact finalized-block fence regressions, six account-only receipt regressions, and two cached funding bypass regressions. Assertions were retained after fixes.

Infrastructure failures were recorded separately: missing root/browser test dependencies were restored without changing dependency lockfiles; the first trusted timeout invocation used a GNU option unsupported by the pinned image's BusyBox and was corrected to `-s KILL`; validator CPU contention caused correct-artifact/short-deadline live failures. The task-owned validator was given lower scheduling priority and live test files are serialized, while explicit concurrent calls within adversarial tests remain concurrent. Policy timeouts, sandbox resource limits, and acceptance assertions were not relaxed. Early failed `test:all` runs returned non-zero.

Repeated Anchor runs on the preserved ledger exposed a test-fixture collision: the fixed private nullifiers already had authoritative NullifierRecords from an earlier passing run. The two fixture nullifiers now use fresh cryptographic bytes per run; the double-spend scenario still reuses one nullifier across its two tasks and retains all original rejection assertions. The five scenarios passed twice consecutively after that narrow fixture fix. No ledger reset, pruning or program change was used.

The final gate used a temporary ignored resource wrapper around the existing `npm run test:all`: it paused only the verified task-owned validator during independent Docker/browser tests and resumed it before Anchor. Clean WSL filesystem page cache was released to reduce memory contention; no files were removed. Windows prevented Cargo from replacing a running seller executable, so the same built binary ran from an ignored copy. The existing local fixture mint/ATA was replenished for repeated tests. These are test-environment controls, not production recovery mechanisms or relaxed deadlines.

A later live run reached the settlement safety margin while initializing the child intended to die after settlement confirmation. The crash fixture now funds inside the initialized child before installing its post-confirmation exit hook. This isolates the intended crash boundary from process startup; the committed six-second timeout, one-second safety margin, child exit assertion and persisted-report/chain assertions remain unchanged. The subsequent separate 108-test recovery gate passed.

The PID fixture also reached its wall timeout before its synchronous 100-fork loop dispatched the `EAGAIN` handler. It now uses a tiny in-container shell artifact that polls the kernel cgroup `pids.events` counter and maps BusyBox's fatal `can't fork` path to the same exit-code-23 sentinel. Its exact exit-code-23 assertion, maximum 100 attempts, ten-second wall limit, 64-PID cap, 128 MiB cap and 0.5 CPU remain unchanged. This makes the test observe the intended PID boundary instead of depending on Node child-process scheduling while the container is already at its process cap.

### Financial transaction reconciliation procedure

1. Retain intent, prepared signature, blockhash/last-valid height, instruction fingerprint, manifest/result/report and all available completion evidence. Do not remove an intent to make a retry possible. Reject orphan, corrupt, mismatched bindings before network mutation.
2. Query original signature with transaction history. `processed`, missing status and RPC errors do not establish successful confirmation. A returned receipt requires `confirmed`/`finalized`, `err === null`, and the matching account outcome. Funding additionally requires the successful initialization transaction's manifest memo. Private settlement requires the corresponding on-chain nullifier record.
3. Read fresh TaskState with program owner/decode validation. Terminal account state prevents a new financial mutation even if local completion is missing. It may prove an outcome while the original receipt signature remains unavailable; report that distinction and require reconciliation rather than inventing a confirmed signature.
4. A transaction whose last-valid block height has not been definitively passed can still land. Keep it `UNKNOWN_FINANCIAL_OUTCOME`; a timeout or `blockhash not found` string is insufficient to sign a replacement.
5. Obtain a finalized slot and the **block height of that exact block**. If unavailable, stop. Beyond the original last-valid height, query signature history again at a context at least that slot, and read account/Clock with `minContextSlot` at least that fence. A finalized failed signature is also non-success evidence. Only absent history after rooted expiry, or finalized failure, together with a fresh non-completed eligible account permits `SAFE_TO_RETRY`; lagging reads remain unknown.
6. Funding eligibility requires absent task and immutable intended parameters. Settlement requires fresh Pending, linked PASS, correct identities/privacy and safe chain deadline; refund requires the chain deadline; cancellation is voluntary and must be before deadline. Never cancel for quality failure. Private replay is prevented by on-chain NullifierRecord.
7. Within an initial controlled submission, rebuilding follows those evidence rules. After process restart, the journal exposes evidence/classification but refuses automatic replacement submission. Operator/reconciliation tooling is a documented future prerequisite, not an implemented worker.

## Security and authority checks

- Existing production HTTPS/host/DNS/IP/redirect checks remain deny-by-default; private IPv4/IPv6, mapped/encoded IP, metadata, credentials, redirect loops and rebinding are rejected. Explicit test fixture allowlists remain test-only. Timeout/response/concurrency limits remain distinct from policy future skew.
- Result commitment precedes random source challenge; seed survives process exit and replays samples. DNS changing to private after seed persistence prevents retrieval without changing the seed.
- Changed artifact bytes, detached evidence and wrong/mutated test bundle hash fail before execution. Tests use the existing committed policy/runner registry; no seller/browser command is accepted.
- Docker retains pinned image, network none, read-only root, UID/GID 65534, no capabilities, no-new-privileges, 128 MiB memory/swap cap, 0.5 CPU, 64 PIDs, bounded files/log output, ephemeral work tmpfs, and two fixed read-only inputs. No Docker socket, host network/PID namespace, signing keys or environment credentials enter the container. Parent wall timer, independent container timeout and lease recovery supplement cleanup on normal/crash/timeout paths.
- Browser/operator hostile/unknown/duplicate/oversized fields are covered by strict committed contract/registration tests. No executable, image, bundle, host path, stdio command, key, destination, treasury or verdict overrides are accepted. Production bundle secret scans and real Chrome screens remain part of regression.
- Voucher journals contain sensitive material server-side only. Browser bundles and public task reports do not contain it. Files request mode 0600; Windows access controls and host identity protection remain deployment responsibilities.
